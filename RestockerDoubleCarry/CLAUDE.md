# RestockerDoubleCarry: notes for agents

Player-facing info is in [README.md](README.md). This file holds implementation details and status. The shared rules and game internals (including how the restocker AI works) are in the root [CLAUDE.md](../CLAUDE.md). The full analysis is in the doc comment at the top of `src/DoubleCarry.cs`.

## Status

With both in hand the clerk handles the box with the shorter walk to its destination first. Racking with two in hand is allowed (not unpacking); unpacking at a shelf still sets the other box down first. New: after unpacking a box that still has leftovers, if the floor box also goes to storage, the clerk picks it up again and racks both. Storage pairs only when the racks have room for every box that may need a place, by the game's own slot rules (`StorageFits`, added after the user's 2026-11-16 note that rack capacity depends on box size and that restocker settings decide unlabelled-rack use). Player-facing description in README.md. Implemented in 1.2.0 (see How it works: `Job`, `ChooseOrder`, `TryRegroup`, Racking enter/exit patches). Not yet reviewed or tested in-game.

v1.1.2 (2026-11-15, after the second in-game test): the user saw the top box stay floating when the restocker put the bottom one down. Cause: a stacking tween left running on the remaining box (on guests nothing killed the lift that `CarryBox(stash)` starts on the other box before the drop), and with empty hands nothing lowered a still-held box. `ArrangeStack` now always kills and restarts the current box's move to the hands, and on `CarryBox(null)` it lowers every other box still in the holder (the leaving box is identified by a `CarryBox_Internal` prefix that records the previous `m_CurrentBox`). Known quirk (not changed): a lowered box sits in the hands with the carry animation off until the host's next search hands it over. Not yet tested in-game.

## Game reference: restockers

Verified in the dumps.

- Restockers are `SupermarketSimulator.Clerk.Clerk` (`RestockerSO.RestockerPrefab`). The old `Restocker` class is unused.
- `Clerk.ManualUpdate` ticks a state machine only when `!PhotonNetwork.IsConnectedAndSlave` (host/offline). The states are `ClerkIdleState`, `ClerkRestockingState`, `RackingState` and `ClerkDropEmptyBoxState`.
- `ClerkIdleState.OnTick` calls `SearchHandler.PerformSearch` every 3 s, plus once on the first tick in Idle. The search fills `BoxTarget` (`IBoxTarget`: `RackSlotBoxTarget`, `StreetBoxTarget`, `VehicleBoxTarget`, or `CarryBoxTarget` for the box in hand), `DisplayTargets` and `RackTarget`.
  - Transitions: `DisplayTargets.Count > 0` → Restocking, `RackTarget` → Racking, back to Idle when the state's `Sequence` completes.
  - A clerk already carrying a box only searches for work for that box.
- States run a `SupermarketSimulator.Sequence.Sequence` of `SequenceTask`s, kept in the list `m_Tasks` and read at every step. Restocking is `[MoveTo, TakeBox, RestockAllDisplays, GoToTrash]`. `TaskStatus`: Running, Fail (ends the sequence), Success (next task).
- `Clerk.CarryBox(box)` sends `ClerkCarryBox_RPC` to guests, then calls `CarryBox_Internal`. That sets `m_CurrentBox`, parents the box to `m_BoxHolder` and tweens it to local zero. `CarryBox(null)` empties the hands without un-parenting anything.
- Level: `NoktaSingleton<EmployeeLevelManager>.Instance.TryGet(clerk.LevelKind, clerk.LevelEmployeeId, out progress)`, then `progress.Level`.
- Interop: `RackSlotBoxTarget` and the other targets don't derive from the `IBoxTarget` interop class. Wrap them with `new IBoxTarget(obj.Pointer)`. Not yet confirmed in-game.

## How it works

- The clerk state machine and its search are described in the game reference above; the search results (`BoxTarget`, `DisplayTargets`, `RackTarget`) pick the next state.
- The mod never replaces a game method. It steers the vanilla states through the search results, using a per-clerk `Plan` with phases:
  - `None` → `FetchFirst`: in a `PerformSearch` postfix, the vanilla search found a job for a non-carried box: restock (`DisplayTargets.Count > 0`) or storage (`RackTarget`, from a street or vehicle box; `Plan.FirstToStorage`). The clerk is at least `MinimumLevel` (`EmployeeLevelManager.TryGet(LevelKind, LevelEmployeeId).Level`), and a second job exists (`TryFindSecondJob` probe). The next `ClerkRestockingState`/`RackingState` run is "fetch only".
  - `TryFindSecondJob` returns a `Job`: a copy of the vanilla restock search (street if `PickUpBoxGround`, then racks; only if `RestockShelf`; product ≠ box 1's), else a copy of the vanilla street-to-rack branch (`PickUpBoxGround`; `GetBoxesFromStreet`, product ≠ -1 and ≠ `m_ExcludedProductId`, not `m_IsBoxOccupied`/`IsTargeted`/occupied, `IsWithinRestockableArea`, `IsMergeAvailableWithBox` else `HasSpaceInRackSlotForProduct`). Never box 1 itself. A storage job also needs `StorageFits(clerk, [box1?, box2])`, with box 1 included when it goes to storage or is the same product (its leftovers go back to the same slots; when box 1 is still in a rack slot, box 2 stands in for it).
  - `StorageFits` never picks a slot for the clerk (vanilla's carried-box search still does that when racking). It replays `RackManager.GetRackSlotThatHasSpaceFor(pid, UseUnlabeledRacks)` box by box with virtual counts: labelled slot not full (capacity of a slot with boxes = `IDManager.BoxSO(Data.BoxID).GridLayout.boxCount`, of an empty one = the incoming box's `Box.BoxSO` layout), else the first unlabelled empty slot (only with `UseUnlabeledRacks`), which is then claimed for that product with the box's capacity. Merges aren't counted on. Rules in the root-shared rack reference (`SupermarketFixes/CLAUDE.md`, Game reference: racks). `ApplyJob` writes the results: displays → Restocking; else an empty non-null `DisplayTargets` plus `RackTarget` → Racking.
  - "Fetch only" = in a `ClerkRestockingState.Enter` / `RackingState.Enter` prefix, remove the tasks after `TakeBox` from `m_Sequence.m_Tasks` (Restocking `[MoveTo, TakeBox, RestockAllDisplays, GoToTrash]`, Racking `[MoveTo, TakeBox, MoveTo, RackBox, GoToTrash]`). They're restored in the `Exit` postfix, and the full list is always restored first in `Enter`. `RackingState` has no clerk field: the clerk is `m_OwnerTransform.GetComponent<Clerk>()` (the ctor stores `owner.transform`). Neither Enter/Exit pair shares an RVA. Racking reserves nothing (Enter: reset result, `Sequence.Start`; Exit: `Sequence.End`).
  - `FetchFirst` → `FetchSecond` (`PerformSearch` prefix, returns false): still holding box 1, so apply job 2, fetch only. `TakeBox` → `Clerk.CarryBox(box2)` makes box 2 current. Box 1 stays parented to `m_BoxHolder`, and that is the "stash".
  - `FetchSecond` → `DeliverFirst` (`ChooseOrder`): for both boxes, `Destination` = vanilla carried-box rule (first slot of `SearchBestFitDisplaySlotsForRestock(box, GetDisplaySlotsRequiredRefillWithoutCondition)`, reservations undone, else merge/space rack slot's `m_InteractionPosition`). `PathLength` = NavMesh path (`SamplePosition` 2 m / 3 m, `CalculatePath`, corners), straight line if that fails. The shorter one becomes current (`HandOver` if it's the stash); vanilla then handles it.
  - Racking (`RackBox`, merge included) runs with the stash in hand: `PlaceBox` re-parents the box into the rack and `CarryBox(null)`s, the stash is lowered, and handed over at the next search.
  - Set down: `RestockDisplay.OnBegin` prefix (the clerk reached a display and is about to open its box; unique RVA). If a plan box is stashed: `DropStash` (CarryBox(stash) → `DropBoxToGround` → CarryBox(box1)), then `MoveAside` puts it next to the clerk (away from the display, else left/right, first free spot by `Physics.CheckBox`) and sends the pose (again after 1.5 s) (`NetworkBox.m_PhotonTransformView.BroadcastCurrentTransform`, only if the host owns it). It becomes `Plan.Floor`.
  - `DeliverFirst`/`Unwind` searches with a box in hand: vanilla (more displays, `GoToTrash` if empty, `RackingState` if leftovers). If no display was ever reached the stash is still in hand; racking with both is allowed (not unpacking), and the stash is handed over once the hands are empty.
  - Regroup (`TryRegroup`, search postfix, once per trip): vanilla just chose `RackTarget` for a `CarryBoxTarget` (leftovers in a plan box), nothing stashed, `Plan.Floor` still on the floor and its `Destination` is storage, and `StorageFits(clerk, [cur, floor])`. Replace the results with a fetch-only Racking run for the floor box (`StreetBoxTarget`; the vanilla `RackTarget` is kept only for the transition), phase `FetchSecond` → `ChooseOrder` → rack both. If the floor box is for a shelf, no regroup: leftovers to storage first, as the user's spec (B).
  - First search with empty hands and `Plan.Floor` still lying there (`IsOnFloor`: active, unparented, not occupied by another): `FetchFromFloor` fills the results itself (`Reset`, `BoxTarget = StreetBoxTarget(box)`, displays via `SearchBestFitDisplaySlotsForRestock(box, GetDisplaySlotsRequiredRefill(pid))`, else `RackTarget` via `IsMergeAvailableWithBox` / `HasSpaceInRackSlotForProduct`, as the vanilla street-to-rack branch; `DisplayTargets` must stay a non-null empty list, since the Idle → Restocking condition reads `.Count`). Nowhere to go, or the fetch run failed: return to vanilla and retry on the next empty-handed search, up to 180 s from the first attempt (`FloorRetrySeconds`). `plan.Floor` is cleared only once the box is in the clerk's hands again, gone, or given up on. While a plan exists `AfterSearch` starts no new trip.
  - `Unwind`: hands empty and nothing stashed or on the floor → plan ends.
- Why the floor box waits for its clerk: `DropBoxToGround_Internal` closes the box, `Box.DropBox` (DOKill, unparent, physics on), `SetOccupy(false)`, `InventoryManager.UnOccupyProduct`, layer Interactable, `StorageStreet.SubscribeBox`. But every street search (`CheckStreetForRequiredProduct` and the street-to-rack branch) also requires `StorageStreet.IsWithinRestockableArea`, so no restocker search picks up a box inside the store.
- Stash = a plan box (`First`/`Second`) that is alive, active, parented to `BoxHolder` and not `m_CurrentBox` (`IsStashed`).
- `Clerk.DropBoxToGround` postfix: also drop the stash (`CarryBox(stash)` + `DropBoxToGround()`), except during `ClerkIdleState.OnTick` (the idle "nowhere to put it" timer drops only the box in hand; the stash is handed over at the next search). This covers `EmployeeManager.DespawnRestocker` and `SetRestockerManagementData` (deactivation).
- Deactivated restocker (`ManagementData.IsActive` false at the next search): drop the stash and end the plan. `SetRestockerManagementData` only drops the box in hand, and only if it is carrying one.
- Errors in the search prefix call `AbortPlan`: hand the stash back if the hands are empty, else drop it. A plan box is never left in the hands.
- Disabling the mod (`ReleaseAll`): hand the stash over if the hands are empty, else drop it. A clerk in `FetchSecond` that is still walking to the other box (box 2, or the floor box when regrouping) with a box in hand drops that box, because the restored full sequence would otherwise take box 2 and strand box 1. Shortened sequences are restored.
- Shortened sequences are tracked only while shortened (`Stripped`: sequence → clerk + original task list), so nothing keeps fired clerks alive.
- Visuals: a `Clerk.CarryBox_Internal` prefix records the previous `m_CurrentBox`; the postfix (runs on host and guests) re-tweens the current box to the hands only if the mod had lifted it (`Raised`; kills its stack tween first) and stacks every other active `Box` child of `BoxHolder` above it. With empty hands it lowers the boxes still held, skipping the previous current box: `GoToTrash` calls `CarryBox(null)` while the trashed box is still parented there; `RackBox.PlaceBox` re-parents into the rack (`RackSlot.AddBox`) before `CarryBox(null)`. Not touched when the previous box is unknown.

## Multiplayer

- Host-only logic. Guests get the game's own RPCs (`ClerkCarryBox_RPC`, `ClerkPickupRack_RPC`, place product, place box, destroy), so they stay in sync.
- `CarryBox_Internal` on a guest never un-parents the previous box either. Without the mod, both boxes sit at the hands' origin, one inside the other. With the mod, the postfix stacks them.
- Display slots are reserved (`DisplaySlot+0x70`) only for the duration of one restocking run, as in vanilla. Both `SearchBestFitDisplaySlotsForRestock` overloads write the field on every returned slot and only `ClerkRestockingState.Exit` clears it (unconditionally, for its dependency list), so the trip-start probe undoes its own reservations. Between legs of the trip another restocker may take the same product's displays. The result is a wasted box trip, not a desync.
- Not handled: a guest joining mid-trip gets the stashed box at its synced world position. It isn't re-parented, because the sync only knows the current box (`NetworkClerk.OnSyncRequested`). It could even be picked up there. The next host `CarryBox` RPC for that box fixes it. If it was taken, `IsStashed` turns false and the trip goes on without it.

## Pitfalls / follow-ups

- `SetDependencies` is inlined into `Clerk.OnBeforeTransition`; don't patch it.
- `TryFindSecondJob` differs slightly from vanilla: it still tries racks after street boxes were found but rejected, and it skips product ids `< 0` (vanilla: `0`).
- Vehicle boxes (`VehicleBoxTarget`) can be box 1 (vanilla picks it) but are never chosen as box 2.
- Mixed trip with different products: the leftovers of the restock box aren't counted in `StorageFits` (vanilla doesn't check leftover space either; a rack box frees its own place when taken). If the storage box takes the last unlabelled slot, the leftovers may find no rack and the idle timer drops them in the store.
- `StorageFits` is a snapshot: another restocker or a player can fill the space before the box is racked (same as vanilla's single-box check).

- Review 2026-11-16 (v1.1.3): no high findings. Applied: `ArrangeStack` now always runs (with `stack=false` when `StackSecondBox` is off) so a box lifted before the option was switched off is still lowered; config text of `MinimumLevel` describes the set-down flow. Accepted/open: unmodded guests see both boxes at the hands' origin (no stacking); the set-down spot assumes the clerk pivot is at its feet and `MoveAside` skips the host-only placement when the host doesn't own the box (confirm in-game that the floor box lands on the floor next to the clerk); the box order swaps over ~0.3 s during the fetch; fail-open paths can still unpack with two boxes if the drop fails twice.
