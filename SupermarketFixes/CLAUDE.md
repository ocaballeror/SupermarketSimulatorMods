## How it works

- **Bug #1** (`RackMoveFix.cs`, `RackDiagnostics.cs`):
  - Racked boxes aren't drawn by their own mesh. `Box.ToggleInstanced(true)` registers a frozen snapshot of their position with `InstancedRenderer`. When a rack is picked up, only the boxes listed in each slot's `m_Boxes` are unregistered.
  - On guests, network updates rebuild rack slots: `RackSlot.Initialize` → `ClearLocalBoxes`. That clears `m_Boxes` but leaves the networked boxes alive and registered, and spawns local copies. Those orphaned boxes become ghosts and duplicates once the rack moves.
  - The fix adopts the networked boxes back into their slot during the rebuild. It also guards the delayed `ToggleInstanced` callbacks that fire for boxes no longer in a slot.
  - Racked boxes stay networked on the host when placed during the session (`ENABLE_DEMATERIALIZE_ON_PLACE` is false); boxes loaded from the save are local copies. A guest who **joins later** gets the networked ones through `NetworkBox.OnPhotonInstantiate`: unparented, kinematic, not in any slot. `ReceiveRackData` spawns a local copy of each as well.
  - `RackMoveFix.Tick` is called from `DiagnosticsBehaviour`. It sweeps every 2 s, guests in a room only, for 60 s after racks first exist, extended by 20 s after each adoption. It adopts each loose, unclaimed networked box that has exactly one local in-slot copy with the same UID + ProductID within 0.3 m, via `Swap(..., origin: null)`. Copies are indexed by (UID, ProductID) once per sweep. It skips carried racks and boxes whose UID + product appears on more than one live networked box. A rejection is logged once per box per window.
  - `Swap` also calls `NetworkBox.DisableNetworkTransformSync(false)`, as vanilla does whenever it racks a box. The rebuild adoption releases claimed (held) boxes instead of pulling them back into the slot.
  - `Release` leaves the box a child of the slot, outside `m_Boxes`. The `RackSlot.Initialize` prefix therefore also captures networked `Box` children of the slot that aren't in `m_Boxes` (unclaimed, not tweening), with `origin = null`, so a later rebuild that lists them swaps them in instead of spawning a copy beside them. `Swap` adds the slot highlight for them. Residual: a guest-side clerk/restocker `PlaceBox` delay coroutine that parents a box before calling `AddBox` could, if a rebuild lands in between, end up with the box listed twice; a later rebuild cleans it up. Not verified whether those coroutines parent early.
  - Join sweep: when a loose box's only same-key rack copy is further than 0.3 m, `Reject` logs the distance (once per box per window, Diagnostics only). While no racks exist, the sweep probes every 10 s instead of 2 s.
  - Clicking a racked networked box itself (instead of the slot) goes `Box.InstantInteract` → `AskAvailability` → host `AvailabilityCallback_RPC` → `NetworkBox.PickUp_Broadcast` → `PickUP_RPC` (to all) → `Box.PickUp`. That path never calls `RackSlot.RemoveBox`, so the slot keeps the entry and its record.
    - Host fix: a `PickUp_Broadcast` prefix first sends the vanilla `NetworkRack.RemoveLocalRackedBox_Broadcast(slotIndex, uid)`. That is `RpcTarget.All`, so it runs on the host at once and reaches guests before `PickUP_RPC`; unmodded guests clean up too. It's skipped if the UID isn't unique in the slot, because clients remove the first UID match.
    - Fallback on every client: a prefix on both `Box.PickUp` overloads calls `RemoveBox` if the box is still in its parent slot. On a guest, a loose networked box picked up next to its single rack copy gets that copy removed and despawned.
    - `RemoveBox` is purely local (lists, records, `InventoryManager.AddBox`, label, reposition). It removes **every** record with the box's UID, and when no record is left it clears the slot (`RackSlotData.Clear`: records, `BoxID = -1`; `RackManager.RemoveRackSlot`). `RemoveFromSlot` wraps it: if another box in the slot shares the UID, it re-adds the records of the boxes still in `m_Boxes` (same `BoxData` instances) and undoes a wrongful clear (`BoxID`, `RackManager.AddRackSlot`, label count). The host still skips its broadcast in that case.
  - The pickup fallback calls `NetworkBox.DisableNetworkTransformSync(true)` (sync on) for a networked box whose parent is a rack slot, as `TakeBoxFromRack_RPC` does; vanilla never does it on the direct path. Only clients with the mod do it. This was a possible lead for Bug #6 (a dropped box hangs for others); unverified.
  - **E (opt-in, host): `TickHost`**, every 2 s when `DematerializeRackedBoxesOnHost` is on, master in a room. For each networked box in `m_Boxes` of a resting rack (not `IsPlacingMode`, no guest carry request answered in the last 10 s via a `StartRackPlacingMode_Response` prefix, no `m_ColliderEnabler` tween), once it has sat there 10 s, it calls the vanilla `NetworkRack.DematerializeBox_Broadcast(slotIdx, uid)` (max 8 per sweep, one per slot per sweep).
    - Vanilla path (verified in the dumps): `DematerializeBox_RPC` (RpcTarget.All) → `RackSlot.DematerializeNetworkedBox(uid)`: first `m_Boxes` entry with that UID; only if it has a `NetworkBox` and isn't `m_IsBoxOccupied`: `RemoveBox`, `InventoryManager.RemoveBox`, `DetachDataBeforeDespawn`, master `PhotonNetwork.Destroy`, `SpawnLocalRackedBox(data)`. A client whose slot holds a local copy (late joiner, or a guest after cause A) does nothing locally; the master's Destroy removes its loose or orphaned networked copy, and `Box.OnDisable`/`OnDestroy` unregister the instanced snapshot.
    - Skipped (logged once per box with Diagnostics): not master-owned (`PhotonView.IsMine`; Destroy would fail after the local removal and leave a duplicate), UID not unique in the slot (every client takes the first UID match), and **the only box in the slot** (no other box or other-UID record). For that last one `RemoveBox` clears the slot, `SpawnLocalRackedBox` then calls `IDManager.BoxSO(-1)` → null and returns null: the box is gone on every client. That is a likely reason the game's own caller (`AddBox` `b__2`, `ENABLE_DEMATERIALIZE_ON_PLACE`) is switched off.
    - Busy boxes (inactive, claimed incl. `IsClaimedByNpc`, tweening, not `Racked`) restart their settle timer. Clerk targets on racks are `RackSlotBoxTarget(slot)`, which hold no box reference (also true for RestockerDoubleCarry).
    - Remaining race: a guest's pickup request (`AskAvailability`) for a box that the host destroys before the request arrives is dropped, and the guest's 3 s timeout handles it. The guest doesn't mark the box occupied before the host answers, so its own `DematerializeNetworkedBox` still runs normally.
    - A guest whose records for the slot differ from the host's (only that one record left) would hit the slot-clear on its side; not expected, since guests get the records from the host.
  - Box UIDs are not unique (the counter restarts per session and guests keep the host's), so all matching uses UID + ProductID.
- **Bug #3** (`StuckBoxFix.cs`):
  - Buying calls `PurchasableProduct.Purchase`, which spawns the box and fakes a "take" click on it. On a guest, the take is a request to the host (`NetworkBox.AskAvailability`, 3-second timeout), and `BoxInteraction` is bound to the box *before* the host answers.
  - Open/close act on `BoxInteraction.m_Box`, but drop and throw only act on what `PlayerObjectHolder` really holds. A box that is bound but never reached the hands gives exactly the stuck state.
  - `PlayerObjectHolder.m_CurrentObject` is never cleared on release, so a box only counts as held if it is also still under the hold point (or in placing mode).
  - The watchdog detects that state, or a host answer that never arrives within 6 seconds. It ends the interaction the way the game does on a refused pickup and resets the `BoxInteraction` flags that `DropBox` resets. It then retries once, but not for racked, inactive or distant boxes. After 3 recoveries of the same box it stops (F9 still works). On the host, a repeat request from the player who already holds the box is granted again.
- **Bug #2** (`GhostHeldItemFix.cs`):
  - `PlayerObjectHolder.HoldObject` overwrites the held object (and its saved layer, `m_CurrentObjectsLayer`) without releasing the previous one, and every drop only releases the current one. Any earlier item still under the hold point stays there forever. All holdable types go through `HoldObject` (Box, FurnitureBox, PaintBucket, FloorBox, OrderPaperBag, IceCreamBucket), always as a direct child of `m_ObjectHolder`.
  - Suspected trigger (guest only): the host's pickup grant arrives after the guest's 3-second timeout, while the player already holds or uses something else. The game logs this ("PickUP_RPC arrived AFTER timeout") but still calls `Box.PickUp`, which binds `BoxInteraction.m_Box` and holds the late box. Result: (a) the previously held item becomes an orphan (the next drop releases the late box instead), or (b) the late box is current with no interaction active, `BoxInteraction` disabled, nothing waiting or placing.
  - `HoldObject` prefix (local player only): records each item's layer before the hold (kept if a re-hold sees "Ignore Raycast"), and notes which object a hold left under the hold point; the scan's first warning for a visible stray appends it. Not logged from the prefix itself: the ice-cream bucket grab (`IceCreamBucket.GrabThis`) calls `ThrowObjectToBin` (restores the box's layer, doesn't unparent it) and then `HoldObject(bucket)`, so the box is briefly displaced in vanilla too before it's hidden. Records are pruned to the hold point's children every scan.
  - Watchdog (`Tick`, 0.25 s, from `DiagnosticsBehaviour`) over the hold point's direct children, after `DelaySeconds`:
    - orphan boxes: dropped by hand like `DropObject` (unparent, recorded layer or "Interactable", `IPlacingMode.PlacingMode(false, null)`, active colliders solid, physics on unless another client owns it), transform sync re-enabled if owned, `IsNetworkOccupied` cleared if host;
    - other orphans: same, but only if the prefix recorded them and they are still on "Ignore Raycast"; anything else is only logged ("Unknown object");
    - a current box in state (b): `DropObject` plus, online, `NetworkBoxInteraction.DropBox_Broadcast` (needs `BoxInteraction.m_Box` = the box). It turns sync on and clears `IsNetworkOccupied` on the sender; `DropBox_RPC` makes every other client run `DropObject` on this player's current object (the same box, since they ran the same `HoldObject`) and clears `IsNetworkOccupied` there, so an unmodded host frees it too.
    - Orphans can't use the networked drop: `DropBox_RPC` drops the receiver's *current* object. So other clients keep showing an orphan in this player's hands.
  - Free-spot check: vanilla only drops a box through placing mode (`OnDrop` → `StartPlacingMode`), whose hologram refuses overlapping spots. `TryDropObject`'s check (`AvailablePosition` = `m_Triggers` empty) is useless outside placing mode, because only `OverlapBoxes` (run from `FixedUpdate` while placing) fills `m_Triggers`. So the mod runs its own `Physics.OverlapBox` per collider (oriented for `BoxCollider`, AABB otherwise, 2 cm margin) on the layers `OverlapBoxes` uses (Default, Interactable, QueryOnly, WallLayer, Ignore Raycast), ignoring triggers, the item, the local player and the hold point. Blocked → retry every scan; F9 tells the player to step back.
  - Skipped: inactive items (the ice-cream bucket box is parked inactive in the hands while the bucket is in use), racked or tweening boxes, the box `BoxInteraction` is waiting for (`IsWaitingAvailability`; its delay restarts afterwards, since the ice-cream/paint box-up flow puts the box in the hands before the pickup handshake), non-box current objects, everything while another interaction owns the hands, and everything during a placement.
  - F9 drops immediately (no delay, also with `AutoRecover` off) but still respects the free-spot check.
- **Bug #5** (`BoxPlaceFix.cs`):
  - Placing needs `m_holdingUse && Box.IsOpen && !m_holdingTake && m_IsBoxOpen && Box.HasProducts` plus the interval (`BoxInteraction.Update`/`CheckForPlacingItem`). `CheckPlaceProductToSlot` never looks at labels: an empty slot accepts any product and `DisplaySlot.AddProduct` relabels it.
  - `m_IsBoxOpen` is BoxInteraction's own flag. It is set by `set_Interactable` (= `IsOpen`), cleared unconditionally by `OnClose`, and set by a `DOVirtual.DelayedCall` after an open click. `OnUse` on an already-open box does nothing but set `m_holdingUse`. So "box open, flag false" blocks placing until close and reopen.
  - Suspected entries: `Box.OpenBox`/`CloseBox` are ignored during the 0.7 s `m_InAnimationTransition` (C pressed right after opening); and online, `PlaceProduct_RPC`/`TakeProduct_RPC` call `Box.OpenBox()` on a closed box (a late host answer after the player closed it).
  - The fix is an `Update` prefix (local player's BoxInteraction only). While Use is held, the box is open and not animating, and the game's own open delay isn't pending (an `OnUse` prefix records open clicks), it sets `m_IsBoxOpen = true`. It also clears `m_holdingTake` if the Take action has been released for 0.5 s, because a release dropped while paused leaves it stuck. Purely local state, so there's no multiplayer impact.
